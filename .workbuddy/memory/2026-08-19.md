## GitHub 更新检查方案定稿（backend/updates.py）

背景：项目更新检查原先用 `api.github.com/repos/<repo>/releases/latest`，未认证按 IP 限流 60 次/小时，共享出口 IP 易触发 HTTP 403。用户诉求：只拿版本号、不想配令牌。

最终方案（用户确认「使用 Git Tag」）：
- 主路径用 `git ls-remote --tags https://github.com/<repo>.git` 直接读 tag，走 git 协议，不经过 api.github.com，无需令牌、不会 403，且即使没发 Release 也能拿到版本。
- 解析：过滤 `refs/tags/`，去掉注解 tag 的 `^{}` 后缀，按语义化版本降序取最新（`_parse_version` → `sorted(reverse=True)`）。
- 兜底：仅当 git 不可用/失败时，才回退到 Release API（可选 `GITHUB_TOKEN`/`GH_TOKEN` 提额）。
- 实测沙箱网络访问不了 GitHub，解析逻辑已用模拟输出单测通过；本机需有 git 且可达 github.com。

教训：GitHub 版本号获取优先选 `git ls-remote --tags`，可规避 api.github.com 60/小时 IP 限流与令牌依赖；`releases/latest` 要求已发布 Release，仓库只有 tag 时会 404。

现象：`/api/agents/wiki/ask` → 502「openwiki 退出码 1」，报错尾部是 `LangSmith tracing disabled - Run failed Tip: ask for a docs change`（这是 openwiki chat 头部 header.js 的渲染，非真正报错）。

排查过程：
1. 调用链：`wiki/ask` → `agent_client.call("openwiki","query")` → `recruit/services/openwiki.py::query()` → `npx --no-install openwiki personal "<问题>"`。
2. `~/.openwiki/wiki` 为空（最近一次 git-repo ingest 是 8-14，当时 config 指向旧路径 `C:\Users\admin\youjidibiao-wiki`；8-17 config 已改到 `C:\Users\admin\Desktop\orchestrator\agents\wiki`，但从未重新 ingest）。
3. 用**系统 Node 24**（`C:\Program Files\nodejs\node.exe`）实测 personal 查询，得到真实根因：**429 Weekly usage limit reached（opencode.ai 网关，工作区 wrk_01M0781KR0GTDQFM0NR71Q1KXA，模型 deepseek-v4-flash 周配额耗尽，4 天后重置）**。openwiki 与项目 `.env`（LLM_BASE_URL=opencode.ai/zen/go/v1, LLM_MODEL=deepseek-v4-flash）共用同一网关，全局阻塞。
4. 陷阱：用受管 Node 22 跑会报 better-sqlite3 NODE_MODULE_VERSION 不匹配（137 vs 127），并伴随 `[safe-delete] 操作失败: ERROR ... Error during a trash operation`——这是 Node 版本 ABI 错配的假象，用户真实环境（Node 24）不出现。排查时务必用系统 Node。

已改 `recruit/services/openwiki.py`：
- 新增 `_extract_error()`：从 openwiki 输出抽取命中关键词（error/failed/429/401/...）的真实报错行，替代原先 `err[-500:]` 截断（真错误被 LangSmith 装饰框淹没）。
- 失败时把完整输出落盘 `logs/openwiki_last_run.log` 便于排查。

后续待办：等 opencode.ai 配额恢复（或换其它 provider/API key）后，需跑 `npx openwiki ingest git-repo`（用系统 Node）把 agents/wiki 合成进 `~/.openwiki/wiki`，wiki/ask 才能正常回答。知识源 config 已在 `~/.openwiki/connectors/git-repo/config.json` 指向 agents/wiki。

### 追加：换 OpenRouter 后定位到真正的第二个坑（safe-delete 拦截）

用户把 `~/.openwiki/.env` 切到 OpenRouter（`OPENWIKI_PROVIDER=openai-compatible`、`OPENAI_COMPATIBLE_BASE_URL=https://openrouter.ai/api/v1`、`OPENWIKI_MODEL_ID=nemotron-3-ultra-550b-a55b:free`）后，openwiki 仍退出码 1，报 `[safe-delete] 操作失败: ERROR ~/.openwiki/skills/.xxx-staging-*: Error during a trash operation: Unknown { description: "Some operations were aborted" }`。

排查结论（重要教训）：
1. **该报错不是 openwiki 的 bug**——openwiki/deepagents/langchain 全量搜不到这串文本（「操作失败」是中文）。来源是 **WorkBuddy 会话环境**：`C:\Program Files\WorkBuddy\resources\app.asar.unpacked\cli\vendor\shim\safe-bin` 里的 `rm/unlink/rmdir` shim 把删除重定向到 `vendor\genie-trash\win32-x64.exe`（回收站工具），该工具在本机失败并输出此报错。触发条件是环境里有 `CODEBUDDY_SESSION_ID`/`CLAUDE_SESSION_ID` + `BASH_FUNC_rm%%` 等会话变量。
2. 验证方法：`env -u CODEBUDDY_SESSION_ID -u CLAUDE_SESSION_ID node .../cli.js personal "你好"` → 立刻成功（exit 0）。带任何 `NODE_OPTIONS=--require` 预加载也偶发成功（时序影响，不可靠）。
3. 修复：`recruit/services/openwiki.py` 新增 `_clean_child_env()`，给 openwiki 子进程剔除 `CODEBUDDY_*`、`BASH_FUNC_rm/unlink/rmdir`、`CLAUDE_SESSION_ID`，并从 PATH 移除含 `safe-bin` 的目录。
4. 另一个注意点：better-sqlite3 原生模块按系统 Node 24（ABI 137）编译，用受管 Node 22（ABI 127）会 NODE_MODULE_VERSION 报错——排查 openwiki 必须用系统 Node（`C:\Program Files\nodejs\node.exe`）。
5. 排查模式：真实报错常被 openwiki 的聊天头部（`LangSmith tracing disabled - Run failed Tip: ask for a docs change`）或装饰框掩盖；用 `OPENWIKI_DEBUG=1` 或完整落盘才能看到 `Error Diagnostics` 里的真实 message。

### 追加 3：删 wiki/openwiki 重下后问答链路实测 + ABI 运行时崩溃修复（2026-08-19 14:3x）

- 场景：用户问「删掉 wiki+openwiki 再重新下载能否回复」。当时 agents/openwiki 与 agents/wiki 已重下（13:30），store 均 ready；`~/.openwiki`（知识脑+`.env`）与 `~/wiki`（llm-wiki 知识源）都在 agents/ 之外，删除 agents 不影响它们。
- 实测 `openwiki.query()` 仍失败：`better-sqlite3` 报 **NODE_MODULE_VERSION 137 (Node24) vs 127 (Node22)** —— 模块按 Node 24 编译，但运行时 npx 拉起 CLI 用了受管 Node 22。
- 根因（`_clean_child_env` 两个叠加 bug）：
  1. Git Bash 把 PATH 传给原生进程时产生**裸盘符坏条目 "C"** 排在首位；
  2. `cand not in parts` 判断跳过了系统 Node 前置——`C:\Program Files\nodejs` 已在 PATH 中后段，导致它排在受管 Node 22 **之后**；npx 生成的 `.cmd` 垫片用 PATH 找 `node` → 命中 Node 22 → ABI 崩溃。
- 修复（`recruit/services/openwiki.py::_clean_child_env`）：切分 PATH 后丢弃空/单字符损坏条目；系统 Node 目录**无条件置顶**（先按 normcase 去重再 insert(0)）；保留 `;`/`:` 两种 PATH 形态兼容。
- 修复后实测：`query()` 返回 `ok=True`，42.5s 返回结构化回答（有机地标公司/产品/概念）。**结论：删 wiki+openwiki 重下即可恢复回复**，前提是 `~/.openwiki`（知识脑 + `.env` 模型配置）不被误删。

### 追加 4：真正根因 = stdin TTY 进入交互模式（2026-08-19 15:4x，本次已修复）

用户报 `/api/agents/wiki/ask` 持续 502「openwiki 执行超时 (60 秒)」。前面几轮修的 safe-delete/ABI 都不是本次超时的主因。本次定位到：

1. **真正根因**：后端由 `run_desktop.bat` 从**控制台**启动（`uv run python -m backend`），worker 及其 openwiki 子进程**继承了控制台 TTY stdin**。openwiki `cli.js` 里 `shouldRunNonInteractively` 判断 `process.stdin.isTTY`，TTY 为真 → 进入**交互式 Ink TUI**（"Ask a follow-up…"），而非一次性 print 模式 → 卡住直到超时。
   - 证据：给超时路径加了落盘诊断（`openwiki_last_run.log` 写 partial stdout/stderr）后，日志出现交互 TUI 的 "enter to send - / for commands - /exit to quit" 及 "Waiting for model output…" 然后 "Run failed / Error terminated"。
   - 关键对比：从 Git Bash（管道 stdin）跑 `openwiki.query()` 每次都成功（10~40s），从控制台启动的 worker 每次都超时——差异只在 stdin 是否为 TTY。
2. **修复**（`recruit/services/openwiki.py::query()`）：给 `subprocess.Popen` 显式加 `stdin=subprocess.DEVNULL`，强制非 TTY，openwiki 走一次性 print 模式。修复后 API 连续 3 次实测 9/10/25s 均返回正确答案。
3. 顺带补强 `_clean_child_env()`：之前漏掉三个非 `CODEBUDDY_` 前缀的拦截变量——`NODE_OPTIONS`（含 `--require genie-safe-delete.cjs`，是拦截的「根」）、`GENIE_TRASH_DIR`、`BASH_ENV`。现一并剔除（NODE_OPTIONS 用正则只剥 genie-safe-delete 的 --require，保留 --use-system-ca）。
4. **遗留问题（未修）**：发现存在**多个 backend 实例**（`uv run python -m backend` 与 `.venv\python -m backend` 并存）导致 worker 进程泄漏（历史有 6 个 openwiki worker、4 个 shop worker 僵尸）。这源于桌面端后端启动逻辑，会加剧 sqlite 锁争用。建议后续修桌面端「重复启动后端/未回收旧 worker」。本次靠 API `/api/agents/openwiki/restart` 重启单个 worker 即生效，但彻底干净需重启客户端。
